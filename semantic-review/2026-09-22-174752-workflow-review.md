# BagSearch — Comprehensive Workflow & Architecture Review

BagSearch is a React + Supabase marketplace for bags in Nigeria. Sellers list products, buyers browse and contact via WhatsApp, and payments go through Flutterwave. The main issues cluster around three areas: the payment flow has a critical architectural gap (no server-side verification), several referenced components don't exist (`AdsLoader.jsx`, `AdcashBanner.jsx`), and the reels SQL schema is significantly out of sync with what the app queries.

**Watch for:**
- **Critical** — `FLUTTERWAVE_SECRET_KEY` and `FLUTTERWAVE_CLIENT_SECRET` are committed to `.env`. Treat these as compromised and rotate immediately.
- **Critical** — Payment `callback` fires client-side with no server verification. A buyer can fabricate a successful response and get an order recorded without paying.
- **Confirmed** — `AdsLoader.jsx` and `AdcashBanner.jsx` do not exist on disk. Any import of these files will throw a module-not-found error at runtime.
- **Confirmed** — `create_reels.sql` is missing `is_active`, `likes_count`, `comments_count`, `shares_count`, `product_id`, `product_name`, `product_price`. The app queries all of them. Reels will load zero rows or throw PostgREST errors until the schema is corrected.
- **Confirmed** — `sellerBankDetails.jsx` saves `is_verified: false`, but `sellerProfile.jsx` gates the "Set Up Payments" prompt on `is_verified: true`. The prompt never clears after a seller saves their details.

---

## High-level view

Routing in `App.jsx` is well-structured: protected routes use `PrivateRoute`, all routes have corresponding `<Route>` entries, and the onboarding overlay renders on top of the products page so the URL stays at `/` and the SEO canonical remains intact. `MobileBottomNav` correctly swaps the middle slot between "List Bag" (sellers) and "New Arrivals" (buyers) and hides on auth pages.

Auth handles email/password, OAuth, and password-recovery links. `AuthListener` catches `PASSWORD_RECOVERY` events from both hash and query-string, which matters for mobile email clients that strip hash fragments.

The Flutterwave integration has the client-side checkout wired correctly, with subaccount routing already coded in `FlutterwavePayment.jsx`. The gap is that `callback` fires in the browser — there is no Edge Function that calls Flutterwave's verify endpoint before inserting the payment record. The entire bank details → subaccount registration step is also missing: bank details are saved locally but never submitted to Flutterwave to create a subaccount ID, so `sellerSubaccountId` is always undefined and every payment goes to the BagSearch master account.

`createProduct.jsx` has solid input validation, file-type checks, rate limiting, and plan-limit gating. The plan-limit gate fails open (allows uploads) when the `can_upload_today` RPC hasn't been deployed, which silently breaks the monetization gate in any new environment.

The reels UI is feature-complete — full-screen snap scroll, desktop theater mode, like/comment/share, upload modal, product linking. None of it works until the database schema is brought in line with what the app queries: seven columns are missing from the `reels` table, a column name in `reel_comments` doesn't match, and the `increment_reel_comments` RPC is called but never defined.

Two `.env` entries — `FLUTTERWAVE_SECRET_KEY` and `FLUTTERWAVE_CLIENT_SECRET` — are server-side API secrets. Without a `VITE_` prefix they won't be inlined by Vite, but being committed to the repo is itself the problem. A separate issue: `VITE_GEMINI_API_KEY` does have a `VITE_` prefix, so it is bundled into the browser build.

<summary>Issues (14)</summary>

1. **Flutterwave secret keys in repo** — `FLUTTERWAVE_SECRET_KEY` and `FLUTTERWAVE_CLIENT_SECRET` are committed to `.env`. Rotate both keys on the Flutterwave dashboard immediately, move them to Supabase Edge Function secrets (`supabase secrets set`), and ensure `.env` is in `.gitignore`.

2. **No server-side payment verification** — `FlutterwavePayment.jsx`'s `callback` fires client-side and inserts a `payments` row based on the browser-delivered response status, without calling Flutterwave's `/v3/transactions/:id/verify` endpoint. Move payment confirmation to a Supabase Edge Function that verifies the transaction ID before recording it.

3. **Missing components crash the app** — `AdsLoader.jsx` and `AdcashBanner.jsx` are referenced but don't exist in `src/components/`. Any component that imports them will throw at runtime. Create these files or remove the imports.

4. **`reels` table missing required columns** — `create_reels.sql` doesn't define `is_active`, `likes_count`, `comments_count`, `shares_count`, `product_id`, `product_name`, `product_price`. The app queries all of them. The `.eq('is_active', true)` filter alone causes every reels fetch to return zero rows.

5. **`reel_comments` column mismatch** — SQL defines `author_name`; the insert in `reels.jsx` uses `user_name`. Comments fail to insert with a PostgREST "column does not exist" error.

6. **`increment_reel_comments` RPC missing** — `reels.jsx` calls `supabase.rpc('increment_reel_comments', ...)` after posting a comment, but this function is never defined in any SQL file. Only `increment_reel_views` is defined.

7. **Bank details `is_verified` broken** — `sellerBankDetails.jsx` saves `is_verified: false`. `sellerProfile.jsx` queries `eq('is_verified', true)` to determine `hasBankDetails`. The "Set Up Payments" banner never clears after a seller saves their bank account. Remove the `is_verified` filter or set it `true` on save.

8. **No Flutterwave subaccount creation** — `FlutterwavePayment.jsx` has `sellerSubaccountId` wired in but it's never populated. There is no UI or backend flow to register seller bank details as a Flutterwave subaccount. Every payment goes to BagSearch's master account; sellers have no automated payout path.

9. **`can_upload_today` RPC fails open** — `useUploadLimit.js` silently falls back to `canUpload: true` on any error, including the function not existing on Supabase. Plan limits are bypassed in any environment where the RPC hasn't been deployed.

10. **Gemini API key bundled into client** — `VITE_GEMINI_API_KEY` is visible in the production JS bundle. Restrict the key to your domain in Google Cloud Console, or proxy Gemini calls through an Edge Function.

11. **"Following" tab in Reels is a dead end** — Both "For You" and "Following" tabs run identical queries. There is no `follows` table or follow concept in the schema. The tab switch is purely decorative.

12. **WhatsApp `replied` state is hardcoded** — `mapBuyerViewRow` hardcodes `replied: false`. The "Replied" state in the buyer views table is never persisted to the database and never changes in the UI.

13. **`fix_products_rls.sql` Step 2 has unresolved placeholders** — `DROP TRIGGER IF EXISTS your_trigger_name_here` silently succeeds but removes nothing. The actual trigger name from Step 1's output needs to be substituted before this file is run.

14. **Account deletion sequencing risk** — `handleDeleteAccount` deletes all product data from Supabase and Pinecone before calling the `delete-account` Edge Function. If the Edge Function fails, the seller's auth account survives with all product data already wiped — an unrecoverable state. Call the Edge Function first and rely on `ON DELETE CASCADE` for data cleanup.

## Flutterwave secrets committed to repo

`.env` contains four Flutterwave values. `VITE_FLUTTERWAVE_PUBLIC_KEY` is safe — it's the checkout public key. The other three are not:

```
FLUTTERWAVE_SECRET_KEY=FLWSECK-70556b71e68152c74fc67f3ccdbfaf20-...
FLUTTERWAVE_CLIENT_SECRET=KmxA1jCk2zr...
FLUTTERWAVE_CLIENT_ID=a0bf8186-...
```

No `VITE_` prefix means Vite won't inline them into the browser bundle. But they're in version control. Anyone with repo read access has them, and any CI/CD misconfiguration could expose them further. Rotate all three keys immediately. Move them to Supabase Edge Function secrets. Add `.env` to `.gitignore` and use `.env.example` with blank values for documentation.

`VITE_GEMINI_API_KEY` is a separate problem — the `VITE_` prefix guarantees it's in the browser bundle. Anyone can find it in DevTools. Restrict it to your domain in Google Cloud Console at minimum; proxying through an Edge Function is the correct fix.

## Client-side-only payment verification

```js
// FlutterwavePayment.jsx — callback runs in the browser
config.callback = async (response) => {
  if (response.status === 'successful' || response.status === 'completed') {
    await supabase.from('payments').insert({ ... });
    onSuccess?.(response);
  }
};
```

`response` comes from Flutterwave's JavaScript SDK in the buyer's browser. A buyer who patches `window.FlutterwaveCheckout` before clicking "Pay" can deliver `{ status: 'successful', transaction_id: 12345 }` to this callback without any money moving. Flutterwave requires server-side verification via `GET /v3/transactions/:id/verify` with the secret key. The fix: `callback` should only record the transaction ID, then call a Supabase Edge Function that verifies the amount and status against Flutterwave's API before inserting the payment row and updating order status.

## Bank details → subaccount gap

The designed payout flow:

```
Seller adds bank details
→ Flutterwave subaccount registered (POST /v3/subaccounts)
→ subaccount_id stored in seller_bank_details
→ buyer pays
→ Flutterwave splits to seller subaccount automatically
```

The current state ends at line one. `sellerBankDetails.jsx` saves to `seller_bank_details` with `is_verified: false` and never calls Flutterwave. `FlutterwavePayment.jsx` accepts a `sellerSubaccountId` param but no caller ever supplies it — `cartPage.jsx` loads the seller's bank record but the `subaccount_id` column doesn't exist on it. All payments accumulate in BagSearch's master Flutterwave account.

The `is_verified` mismatch is a symptom of this incompleteness: "verified" was presumably meant to mean "Flutterwave confirmed the subaccount", but since that API call is never made, the field is always false, and `sellerProfile.jsx`'s `hasBankDetails` check is perpetually `false` even for sellers who have entered their details.

## Reels database schema vs. app queries

`create_reels.sql` defines the `reels` table with: `id`, `user_id`, `seller_name`, `caption`, `video_url`, `thumbnail_url`, `likes` (integer), `views`, `created_at`.

`reels.jsx` issues:

```js
supabase.from('reels').select('*').eq('is_active', true)
```

`is_active` doesn't exist → PostgREST returns a 400, or the filter is ignored depending on the Supabase version, and the client receives an empty array. The app then accesses `reel.likes_count` (SQL has `likes`), `reel.comments_count`, `reel.shares_count`, `reel.product_id`, `reel.product_name`, `reel.product_price` — all undefined.

`reel_comments` defines `author_name`; the app inserts `user_name`. The `increment_reel_comments` RPC is called after every comment post but is never defined — the `.catch(() => {})` silently swallows the error.

Required migration additions to the `reels` table: `is_active boolean NOT NULL DEFAULT true`, rename `likes → likes_count`, add `comments_count integer DEFAULT 0`, `shares_count integer DEFAULT 0`, `product_id uuid`, `product_name text`, `product_price numeric`. In `reel_comments`: rename `author_name → user_name`. Add the `increment_reel_comments` function matching the `increment_reel_views` pattern.

## Missing ad-gate components

`AdsLoader.jsx` and `AdcashBanner.jsx` don't exist in `src/components/`. No file in the codebase currently imports either of them, so there's no immediate crash. However, if these files were part of the planned ad-gate flow (sellers watch an ad before uploading), that gate is entirely absent from `createProduct.jsx`. The only upload gate present is the `useUploadLimit` plan-limit check.

## `can_upload_today` fails open

```js
// useUploadLimit.js
} catch {
  setState(s => ({ ...s, loading: false }));
  // canUpload remains true — unlimited uploads allowed
}
```

If `can_upload_today` hasn't been deployed to Supabase, this catch silently enables unlimited uploads for every seller. For a monetization gate, failing open is the wrong default. The catch block should either set `canUpload: false` or at minimum log a warning that the RPC is unreachable.

## `fix_products_rls.sql` placeholder not filled in

Step 2:
```sql
DROP TRIGGER IF EXISTS your_trigger_name_here ON public.products;
DROP FUNCTION IF EXISTS public.your_function_name_here();
```

`IF EXISTS` suppresses errors, so running this as-is appears to succeed but removes nothing. The intended use is: run Step 1, read the trigger name from the output, substitute it here, then run Step 2. Committing the file with placeholders intact creates false confidence that the broken trigger has been removed.

## Account deletion sequencing

`handleDeleteAccount` in `sellerProfile.jsx` runs in this order:
1. Calls `deleteFromPinecone(productIds)` and `supabase.from('products').delete()`
2. Deletes views, search history, saved items, orders
3. Calls the `delete-account` Edge Function to delete the auth user

If the Edge Function fails after steps 1-2 complete, the result is an auth account that exists with no products, no history, and no way to re-add data. The seller is locked out functionally but not technically deleted. Reversing the order — Edge Function first, then cascade-driven cleanup — means a failure at any point leaves the account intact and recoverable.
